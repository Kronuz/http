# The Asio transport: TLS and limits

The opt-in transport features beyond buffered `send()`/`write()`. For owned
streaming responses see [OWNED_STREAMING.md](OWNED_STREAMING.md).

## Optional HTTPS transport

`HttpAsioService(handler, reactors, limits, http::Tls{context, failed})` serves TLS with `context` (plain HTTP without one); `http_asio_tls.h` defines that constructor, so only a TLS service includes it and links OpenSSL. The caller configures certificates and verification policy (`reactor::tls::server_context` builds a server's). `Limits::tls_handshakes` caps the handshakes in progress across the loops (64 by default), and `Limits::tls_handshake` gives each one absolute deadline from its accept (five seconds by default); `max_clients` bounds TLS connections as it does plain ones. The service retains the context through original operations. The connection is a `detail::TlsStream`: OpenSSL reads and writes the non-blocking socket through a BIO over it, and a call that would block waits for the socket's readiness, so an idle TLS connection holds the SSL object and its session state and no record, staging or BIO buffers ([perf/idle.md](perf/idle.md)).

The common HTTP parser and response path operate on the plaintext stream. The connection's input keeps one owned read pending while a handler runs or an owned-stream reply waits; it reads up to 4096 bytes ahead, and the bytes it took go to the next read, first and in order. Fatal read errors close the current owned-stream exchange. The plain-TCP service needs no OpenSSL.

The parser is http-parser in its strict default (it rejects what request smuggling relies on, and the connection is dropped without a response). The trailer section of a chunked request goes to `Request::trailers` and never to `Request::headers`, so a trailer cannot stand in for a header a front end set or removed. A `CONNECT` request is answered and the connection closes: the service opens no tunnel, a `CONNECT` has no content (RFC 9110 section 9.3.6), and nothing after its header section is read as a request. The connection also closes after an HTTP/1.0 request with `Transfer-Encoding` (RFC 9112 section 6.1).

## Request lifetime, admission and shutdown

A handler is a `task::task<void>` that the connection, itself a task on the reactor's scheduler, awaits as a child, and the request and response writer stay alive until it completes. The session's stop token reaches only the next request's reads and the TLS handshake, so no frame is destroyed under a running handler. A client hang-up and a shutdown reach the handler as `Request::cancel(reason)` (`http::disconnected` or `task::cancel_reason::shutdown`), which requests the request's `task::cancel_token` (`Request::cancel_token()`); reads then stop at their next checkpoint and writes complete. Details are in `docs/mechanisms/coroutine-handlers.md`.

Every bound is a field of `http::Limits`, which the constructor takes whole, so no bound is set in two places or forgotten: `max_clients` (1024), `max_in_flight` (1024 per loop), `idle_timeout` (75 s), `header_timeout` (30 s), `inactivity_timeout` (60 s), `request_timeout` (off), `shutdown_grace` (5 s), `max_body` (16 MiB), `tls_handshake` (5 s) and `tls_handshakes` (64). Zero turns a timeout or a cap off; a timeout outside zero to 24 hours, or a `max_in_flight` past `int`, throws `std::invalid_argument`.

A request enters the reactor's `AdmissionGate` (`max_in_flight`) at its first byte and leaves it when its response is settled, so `wait_requests()` counts a request whose headers are still arriving. Past the cap the connection answers `503` with `Retry-After: 1` at headers-complete and closes before reading the body. `reactor(i).gate().rejected` counts the refusals. A client trickling its headers holds its slot for up to `header_timeout`; with the defaults one loop cannot fill (`max_clients` 1024 against 1024 per loop), but with `max_clients` off, or above one loop's cap, slow-header peers can fill a loop's gate and its other requests get `503` until their header timeouts close them. A handler can add a cap of its own by throwing `RequestRejected(503, ..., retry_after_seconds)` from `create_extension`.

A buffered body is capped by `max_body` (16 MiB by default, 0 for none). A `Content-Length` over the cap is answered `413` at headers-complete without reading the body, and a chunked body is answered `413` when it passes the cap. Bodies that stream (`wants_body_stream`, `on_request_body`) are not capped.

`stop()` cancels every running request, lets their responses finish, then waits `shutdown_grace` (5 s by default) before it closes the sockets that peers still hold, and returns after at most the grace once more. Idle keep-alive connections end at once. A caller that lets requests finish first runs its first part in steps: `stop_accepting()` closes the listeners, after which a request whose first byte comes later is answered `503` (no `Retry-After`) on the connection it came on and every reply says `Connection: close` and closes its connection; `wait_requests(token)` returns true once no request is in flight, or false at its token; `cancel_requests()`; then `stop()`. An accepted connection that sent nothing holds no request, so it never holds `wait_requests()`.

`close_idle()` closes the connections waiting for a request at once and every other one after its reply, which says `Connection: close` (an operator's flush of client connections). It returns at once, from any thread, a handler's too; each loop closes its idle connections on its next turn. `close()` and `destroy_roots()` are task's later teardown phases: the schedulers drop what is posted, then the tasks still suspended (a handler that ignored its token) are destroyed; destruction runs any phase not yet run.

`max_clients` caps sockets at the accept, before destination dispatch, plain and TLS alike; `connection_stats()` reports its counts. A connection's session honors `SessionContext::stop` in its waits.

For TLS, the accept timestamp starts the handshake deadline, so destination queue wait consumes it, and the session's stop token ends a pending handshake. TLS allocation follows the handshake cap and elapsed-deadline checks.

`request_timeout` sets one absolute header/body deadline per request. Fragments do not renew the deadline; buffered replies use the remaining budget. A handler reads it as `Request::deadline()` (`time_point::max()` when off) and bounds its own waits by it. It adds no deadline to arbitrary direct streaming writes.

Three finer bounds apply to every connection, plain and TLS. `idle_timeout` bounds the wait from a connection's start (after a TLS handshake) or a reply's end to the next request's first byte. `header_timeout` bounds the time from that first byte to the end of the headers, so trickled headers cannot hold a connection. `inactivity_timeout` bounds each body read and each 64 KiB of a buffered reply, so a slow transfer that keeps moving completes while a stalled one ends. None bounds a running handler: a held poll whose headers are complete and whose body is unread trips neither. Owned streaming replies keep their own deadlines.

`Tls::failed`, a `TlsFailureHook`, is called with a `TlsFailure` for every TLS connection that ends before serving: `deadline` or `handshakes` (the handshake bounds), and for a failed handshake `protocol` (not TLS at all, such as plain HTTP), `version`, `cipher`, `certificate` (the client refused the server's), or `other`. Connections `max_clients` refuses at accept never reach it; the reactor's admission counters report those.

Handlers can throw `http::RequestRejected(status, body, content)` from header/body admission to send a bounded rejection before consuming the request body. Status must be 400–599 and body at most 512 bytes; content selects fixed text or JSON framing. The transport closes after writing the rejection, with a one-second write bound. The exception derives from `std::invalid_argument` for existing admission catches.

`connection_observer()` returns read-only shared transport admission state for background metrics. The observer outlives the HTTP service safely. These transport extensions require the pinned reactor headers (`CMakeLists.txt`).
