# T6 and T7 on Linux metal: did task handlers close the CPU and latency gap?

> Status: CURRENT (2026-11-03) the measurement behind K6, K7 and K9 of `docs/status/task-handlers.md`; nothing in the library changed.

Design rows: `docs/design/task-handlers.md` T6 (throughput, p99, server CPU per request), T7 (allocations per request), S7, D8 and Q3.
The question: with handlers on `task::task` and the connection loop still `asio::awaitable` (the bridged loop), does
http match head (A, the Asio-awaitable handlers) on req/s, p99 and server CPU per request, and do the frames cost
more allocations.

`bench/t6.sh run` verifies every series answers the same 103 bytes (`bench/verify.py`), then `bench/ab.sh run` rotates the

### Harness bugs found by the dry run (both fixed before the metal run)

1. `bench/run.sh` computed CPU per request as `u[n-1]-u[0]` with `n` unset on the first `RUSAGE` line, so `u[0]` was empty
   and the figure was the process's total CPU since start (start-up and the 1 s warm-up included), 25 to 30 percent over the
   timed window (14.1 against 10.75 us/req on the c7a dry run). Every earlier `server CPU` figure from `run.sh` (the
   CHANGELOG and `docs/perf/timeouts-cpu.md` tables, S1's smoke runs) carries that extra, equal across series but not
   comparable with this note. It is fixed (`BEGIN { n = 0 }`) and cross-checked with `/proc/PID/stat` and the sum of
   `/proc/PID/task/*/schedstat`.
2. `bench/ab.sh` with two `EXTRA` series printed its series list with a newline, so `awk` picked two series per rotation
   slot and the first and last never ran (`server did not start` in the log). Fixed.


## Verdict

K6 (T6): **met on Linux.** B1 is inside the A/A band or better than A on req/s, p99 and server CPU per request for
`http` and `httpr` at 8 and 64 connections, with both compilers. No cell of B1 is worse than A. `http` is parity
(within 2% on every metric); `httpr` is about 2% better at 8 connections (borderline: outside the band by the band rule, noise by `ab_compare`) and 3 to 3.5%
better at 64 (outside the band); `httpt` and `httpb` are 19 to 43% better. B0 (without C3's inline resume) is within the band on `http`
and `httpr` req/s but worse than A on `http` p99 (+4.5 to +13%) and slightly on `http` CPU (+0.6 to +1.8%); C3's inline resume
is what takes B1 from "about equal" to "equal or better" on the plain kinds.

K7 (T7): **met.** Operator-new calls per request are 2.00 for A, B0 and B1 on `http`, `httpr` and `httpt` at 1, 8 and 64
connections with either compiler, and 9.00 against A's 10.00 on `httpb`. Asio handler invocations per request: B1 equals
A (1.00 `http`, 2.00 `httpr` and `httpt`) and is below it on `httpb` (7.00 against 8.00); B0 pays one more than A on every
kind (2.00, 3.00, 3.00; `httpb` 11.00 against 8.00). That is the queue trip C3's inline resume removes.

D8 (K9): see the recommendation below. This note measures; it changes no library code.

## The four axes

1. Time: above (req/s, p99). B1 equals A on the plain handler and is up to 43% faster on the streamed body.
2. Throughput: the same numbers; the server is saturated, 390 to 430 thousand requests per second on 2 reactors for
   `http`.
3. Memory: allocations per request above (equal or lower). Resident set size was not measured in this window.
4. Disk: the bench binary is 13 to 14% smaller for B (clang 2,111,600 to 1,810,792 bytes, g++ 2,180,312 to
   1,902,672).

Savings: for `http` and `httpr` there is none worth stating (parity to 3.5%). For a streamed 1 KiB body B1 spends 6.5 us
of server CPU per request against A's 9.3 (clang, 8 connections), 2.8 us less. At a sustained 100,000 such requests per
second that is 0.28 cores, about 2,400 core-hours a year; at the instance's on-demand rate (c7i.metal-24xl $4.284 per
hour over 96 vCPUs, $0.0446 per vCPU-hour) that is about $109 a year per 100,000 requests per second. Small.

## Recommendation for K9 / D8 (the owner rules)

Keep the connection loop as the private `asio::awaitable` (the bridged loop); do not build the task loop, and Q3 does not
arise. T6 and T7 pass with it on Linux with both compilers, with the task C3 code (task:fb7d9bf, equal to d080786 in
code). The pin in http's CMakeLists (task:6558c2e) predates task:d080786, which gives each scheduler scope its own
